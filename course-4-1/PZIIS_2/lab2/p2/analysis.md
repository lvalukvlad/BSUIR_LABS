# Анализ Secure Notes Lab по методике (часть 2)

## Краткое описание системы

Веб-приложение на Flask + SQLite: регистрация/вход, заметки (открытый текст), секреты (Fernet), выход. Локальный запуск на `127.0.0.1:5050`.

## Результаты по аспектам

### Политика безопасности ОС
- Приложение не требует root.
- Риски: доступ ОС-пользователя к `instance/secure_notes.db` и `instance/fernet.key` → расшифрование всех секретов.
- Рекомендация: права `600` на key/db, отдельный системный пользователь, диск с шифрованием.

### Компоненты и взаимодействие
- Плюсы: PBKDF2, CSRF, ORM, изоляция по `user_id`, шифрование секретов.
- Риски: XSS при отображении HTML без экранирования (Jinja по умолчанию экранирует — ок); нет rate-limit на логин (брутфорс); ключ Fernet рядом с БД.

### Сеть
- Плюсы: bind на localhost; SameSite=Lax; HttpOnly.
- Риски: без TLS cookie можно перехватить в небезопасной сети, если открыть порт наружу; `SESSION_COOKIE_SECURE` выключен по умолчанию.

### Конфиденциальность
- Секреты в БД — ciphertext; пароли — хэши.
- Ключ шифрования — единый для приложения (не per-user KDF от пароля): компрометация ключа = компрометация всех секретов.

## Меры усовершенствования
1. Per-user ключ (KDF от пароля / Argon2 + обёртка DEK).
2. Rate limiting / блокировка после N неудачных входов.
3. TLS (nginx/caddy) + `Secure` cookies.
4. Аудит-лог доступа к секретам.
5. Content-Security-Policy, отключение debug.
6. Резервное копирование с отдельным хранением ключей.

## Рекомендации по безопасному использованию
- Не публиковать порт 5050 в интернет без reverse-proxy и TLS.
- Не копировать `instance/` в публичные репозитории.
- Использовать длинные уникальные пароли.
- После демонстрации удалять учебную БД/ключ или ротировать ключ.
- Запускать от непривилегированного пользователя ОС.
