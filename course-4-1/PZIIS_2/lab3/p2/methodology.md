# Методика оценки безопасности кода

## Цель

Оценить, насколько реализация минимизирует риски нарушения конфиденциальности и доступности при невалидном вводе, аварийных ситуациях и нагрузке, с акцентом на работу с данными в оперативной памяти.

## Объект оценки

Исходный код приложения и поведение процесса в ОЗУ (дампы после create / update / delete).

## Этапы

1. **Инвентаризация данных** — какие сущности конфиденциальны / нет; где хранятся (ОЗУ, диск, сеть).
2. **Валидация ввода** — реакция на пустые, длинные, некорректные значения; сообщения об ошибках без утечки секретов.
3. **Жизненный цикл секрета в ОЗУ** — как долго plaintext живёт в памяти; есть ли шифрование/хеширование сразу после ввода; затираются ли буферы.
4. **Удаление и обновление** — исчезают ли маркеры plaintext из дампа после update/delete; остаются ли копии (интернирование строк, буферы HTTP).
5. **Аварийные сценарии** — попадёт ли секрет в лог, файл подкачки, core dump по умолчанию; настройки окружения.
6. **Нагрузка и ресурсы** — рост RSS/CPU при типовом CRUD; утечки объектов (неограниченный рост словарей).
7. **Сравнение вариантов** — баллы по чек-листу (ниже) для своей реализации и предоставленной.

## Чек-лист (0 — нет, 1 — частично, 2 — да)

| ID | Критерий |
|----|----------|
| C1 | Конфиденциальные данные не хранятся в ОЗУ открытым текстом дольше, чем нужно для обработки |
| C2 | После ввода применяется шифрование или необратимое хеширование |
| C3 | Есть попытка затирания временных буферов plaintext |
| C4 | Неконфиденциальные данные явно отделены от конфиденциальных |
| C5 | Валидация обязательных полей на сервере |
| C6 | Секреты не пишутся в логи приложения |
| C7 | После delete маркеры plaintext не находятся (или существенно реже) в дампе |
| C8 | Есть наблюдаемость ресурсов (PID, RSS/CPU) для анализа |

Итоговый уровень: 0–5 низкий, 6–11 средний, 12–16 высокий (относительно учебных критериев).
