Ответы берутся из реальной связки OSTIS:

POST /api/kb/search/ — серверный поиск по базе (что именно делает бэкенд, в этом репозитории не видно, но контракт реальный: query, lang, ответ в JSON).
Прямой путь по графу: по тексту ищутся sc-ссылки (searchLinksByContents), узел через nrel_system_identifier / nrel_main_idtf, затем команда ui_menu_summary (getDescriptionByAddr / doCommand) — это агент над загруженной SC-памятью.
Заготовленный «фейковый» текст в модуле — только сообщения, когда ничего не нашлось («не найдено определения», «не удалось выполнить как действие» и т.п.), плюс постобработка/обрезка уже полученного ответа.

Как система ищет в базе знаний (вкратце)
Подготовка строки: правки опечаток (RU), нормализация (регистр, пунктуация…).
Намерение: определение / действие / навигация / другое — от этого зависит порядок шагов.
Кандидаты: исходный текст + варианты вроде «что такое …» / what is … + алиасы из QUERY_ALIASES.
Два параллельных механизма:
для каждого кандидата — запрос /api/kb/search/; ответы ранжируются (сильный / слабый по эвристикам);
для части сценариев — найти узел по тексту идентификатора в памяти и взять сводку (ui_menu_summary).
Постобработка: обрезка служебных фрагментов, для RU — укорочение до пары предложений.

Да, путь для EN есть: везде передаётся lang, для английского свои префиксы в detectIntent, в кандидаты добавляется what is …, в searchKB уходит { query, lang }.

Но: ответ будет только если в базе есть соответствующие английские идентификаторы/определения (или бэкенд умеет сопоставлять EN-запрос с тем, что в БЗ). Если в БЗ в основном русские формулировки, на EN качество может быть хуже или ответа не будет — это ограничение наполнения БЗ, а не отключения языка в коде.

Модуль getDescription — это слой между полем ввода AskAI и базой знаний. Он не рисует интерфейс: он принимает текст вопроса и язык, нормализует запрос и строит несколько вариантов формулировок, в том числе через алиасы — синонимы и опечатки. Дальше он понимает тип вопроса — скорее определение, действие или навигация — и в двух направлениях ищет ответ: через HTTP-поиск по базе (/api/kb/search/) и, когда возможно, находит элемент в семантической сети по тексту и запрашивает краткую сводку стандартной командой ui_menu_summary. Ответы не подставляются с потолка — они из БЗ или агентов; если ничего не найдено, пользователю показывается явное сообщение об отсутствии. Для английского логика та же, но нужно, чтобы в базе были английские данные.

command.ts — тонкая обёртка над HTTP-эндпоинтом sc-web POST /api/cmd/do/. Она запускает пользовательскую/интерфейсную команду OSTIS по числовому адресу команды (cmdAddr в SC-памяти) и передаёт аргументы — тоже числа (обычно sc-адреса элементов).

action — это адрес узла в SC-памяти, который идентифицирует инициированное действие (задачу), по которому платформа потом строит результат. Тип в интерфейсе минимальный; сервер может отдавать больше полей, но клиент здесь типизирует только action.

command.ts — один экспорт doCommand. Он отправляет на POST /api/cmd/do/ форму: поле cmd — адрес нужной ui-команды в базе, дальше 0_, 1_, … — числовые аргументы, обычно sc-адреса. Сервер инициирует действие в метасистеме и возвращает action — узел запущенной задачи. Дальше остальной код не в этом файле: он ждёт завершения и читает результат через ts-sc-client. Так AskAI вызывает ui_menu_summary, а SCn — команду полной окрестности.

src/api/sc/client.ts. Файл инициализирует и держит «живым» подключение браузера к sc-server по протоколу WebSocket, через библиотеку ts-sc-client.

На выходе модуля два синглтона:

client — экземпляр ScClient: поиск по шаблонам, ссылки, содержимое, события и т.д.;
helper — ScHelper(client): вспомогательные операции поверх того же соединения (например, получение системного/основного идентификатора узла).

Остальной код приложения не создаёт новый ScClient, а импортирует уже готовый client (и при необходимости helper) из @api / @api/sc.

Логика:

Повторный вход (после обрыва): с предыдущего client снимаются слушатели error / close, чтобы не копить утечки и двойные переподключения.
Создаётся new ScClient(SC_URL) — фактически новое WebSocket-соединение с sc-server.
new ScHelper(client) — helper всегда соответствует текущему клиенту.
Обработчики onError и onClose одинаковые: setTimeout(getClient, TIMEOUT) — через 2 с снова вызвать getClient (пересоздать клиент).

client.ts поднимает единственный для приложения ScClient из ts-sc-client: он открывает WebSocket на SC_URL — по сути на sc-server метасистемы. Рядом создаётся ScHelper для вспомогательных запросов к той же памяти. Если сокет падает или закрывается, через 2 секунды модуль пересоздаёт клиент и снова вешает обработчики — это примитивный автопереподключение. Все модули вроде getDescription или SearchField дальше используют этот же client, а не открывают второе соединение сами.

common.ts задаёт адреса и стартовый сценарий. SC_URL — WebSocket на sc-server (по умолчанию 8090, путь ws_json). API_URL обычно пустой: тогда все /api/... и /scg идут на тот же хост, что и React, а в разработке прокси пересылает их на sc-web 8000 без CORS. Если в .env прописали прямой 8000, в react-sc-web при открытии с 3000 это сбрасывается в пустую строку, чтобы всё шло через прокси. Плюс константы myself и ui_menu_view_full_semantic_neighborhood — из них собирается DEFAULT_COMMAND_PATH: стартовая страница в SCn для точки входа в систему.

AskAnswer — экран чата AskAI. При открытии он читает из react-router state первый вопрос и флаг «это с кнопки-подсказки». Один раз вызывается fetchAnswer: либо обработчик подсказки, либо getDescriptionById к базе знаний. Ответ кладётся в Redux-историю, список рисует AskElement, внизу AskInput для следующих вопросов. Пока идёт запрос — спиннер; пустая отправка — тост; ошибка или пустой ответ — в историю попадает понятное сообщение пользователю. После каждой новой записи список прокручивается вниз.

AskPage — это только витрина AskAI: заголовок, готовые вопросы-кнопки и поле ввода. Она не запрашивает базу: при отправке или выборе сценария делается navigate на вложенный маршрут answer с state: текст вопроса и флаг, пришёл ли вопрос с подсказки. Пустая отправка обрабатывается в AskInput и показывает короткое предупреждение. Вся работа с getDescriptionById и историей — уже на *AskAnswer.

AskInput — обёртка над полем и кнопкой: значение либо живёт внутри компонента, либо полностью приходит с родителя через value. При вводе он шлёт onChange наверх. Enter обрабатывается через preventDefault на keydown и отправку на keyup. Пустая строка — onEmptySubmit, иначе onSubmit. В неконтролируемом режиме после успешной отправки поле сам очищается; на экране ответа AskAnswer держит inputValue и очищает его после запроса. Реф с refSetter ведёт на настоящий <input>.

AskHintButtons — это только список кнопок с заранее заданными вопросами из hintButtons.ts. Для текущего языка useTranslate выбирает текст кнопки. По клику делается navigate на answer с state: этот же текст как query и isHintButton: true. Сам компонент не ходит в сеть; AskAnswer по флагу вызывает getHintButtonHandler: в нашем ostis это сопоставление с button.text[lang] и готовый handler, в react-sc-web — вызов getDescriptionById к базе знаний.

hintButtons.ts хранит массив подсказок: для каждой — текст на ru/en и handler с готовым ответом через Promise.resolve, без запроса к базе. getHintButtonHandler по текущему языку и строке вопроса находит соответствующую кнопку и возвращает её handler. AskAnswer только await-ит этот handler. Чтобы всё сходилось, текст с кнопки после translate должен совпасть с button.text[lang] с учётом trim.»

AskMain — родительский роут для /ask-ai/: в div.wrapper стоит Outlet, куда подставляются AskPage или AskAnswer по вложенному пути. Общий Layout с панелями навешивается в *Router выше. В react-sc-web при размонтировании AskMain вызывается resetHistory, чтобы очистить Redux-историю диалога; в ostis-metasystem в этом файле только Outlet, без сброса.

requestDialogHistorySlice — Redux Toolkit-слайс с массивом requests: каждая запись — query и answer. addInHistory дописывает пару в конец, AskAnswer мапит список в AskElement. resetHistory очищает чат; в react-sc-web он вызывается при выходе из AskMain, в ostis в AskMain этого нет — история может сохраняться в сторе. От requestHistorySlice это отдельно: там история команд интерфейса, здесь — только диалог AskAI.

Scn — обёртка над Scn из ostis-ui-lib (ScnBase): по числовому адресу узла действия action загружает дерево SCn (текстовое структурное представление результата команды), показывает загрузку, ошибки и долгую загрузку (таймаут перевода), даёт переход «домой», если данных нет. Также обрабатывает клик по элементу в дереве: запуск команды полной семантической окрестности для выбранного адреса.

Scn получает action — адрес действия в памяти — и через getScnTree подгружает дерево SCn. Пока ждём, onRequestStarted включает загрузку; если ответ долгий, срабатывает useLazyTimeout и показывается предупреждение. При ошибке перевода с известным текстом таймаута запрос повторяется. Успех — ScnBase рисует SCn с scgUrl. Клик по элементу вызывает onInitiateAction: doCommand для ui_menu_view_full_semantic_neighborhood по адресу узла и возврат нового action. Если дерева нет и загрузки нет — считаем, что элемент недоступен, показываем кнопку домой на DEFAULT_COMMAND_PATH. В react-sc-web к этому добавлены контекстные подсказки по разметке SCn при наведении; в ostis файле их нет.

SearchField — глобальный поиск по тексту в интерфейсе: пользователь вводит подстроку, система через WebSocket (**ts-sc-client**) ищет содержимое sc-ссылок, показывает список подсказок; по выбору варианта резолвит строку в sc-элемент и переходит к команде просмотра в активном формате (SCn/SCg и т.д.) через useScNavigation.
Это как раз тот сценарий «контекстные подсказки при вводе», но данные подсказок из загруженной SC-памяти, а не из статического словаря.

SearchField — поиск по базе в реальном времени. Ввод дебаунсится на 300 ms, затем searchLinkContentsByContentSubstrings по WebSocket ищет тексты sc-ссылок, содержащие подстроку; длинные строки отрезаем, результат уникализируем и сортируем по длине. Пользователь выбирает строку — searchAddrById находит адрес элемента, goToActiveFormatCommand открывает его в текущем формате. Это не заглушка: данные из подключённой SC-памяти. В react-sc-web добавлены клавиатура, тема и опциональный ScTag.

Как подсказки «берутся из SC-памяти»
В коде вызывается метод ts-sc-client:
client.searchLinkContentsByContentSubstrings([searchValue])
Он отправляет запрос по уже открытому WebSocket на sc-server. Сервер в работающей sc-machine смотрит в загруженную SC-память: среди sc-ссылок (элементов, у которых есть текстовое содержимое) ищутся те, в чьём тексте встречается введённая подстрока. В ответ клиент получает набор строк — это и есть варианты в выпадающем списке.
То есть это не отдельная таблица «подсказок» в React и не заранее скачанный JSON: это живой поиск по содержимому ссылок в том графе, который сейчас в памяти у машины.

Как эти тексты «попадают» в SC-память
Память не наполняется из поля поиска. Она один раз (или после пересборки) загружается из бинарного образа базы (у вас в конфиге это связка repo.path → sc-builder → kb.bin → storage = kb.bin при старте sc-machine).
Источник знаний — исходные SC-модели (каталог sc-models и т.п.): файлы .scs, где задаются узлы, связи и тексты — например:
идентификаторы (nrel_main_idtf, nrel_system_identifier и др.) — это как раз ссылки с текстом;
определения, пояснения, SCn-тексты и другие фрагменты тоже кладутся в содержимое ссылок при сборке.
sc-builder разбирает эти тексты и строит бинарное представление графа. sc-machine при запуске загружает этот граф в sc-memory. После этого любой поиск по подстрокам в ссылках работает уже по этому загруженному содержимому.
Дополнительно в сессии в память могут попадать новые элементы и ссылки (агенты, действия пользователя, команды), и они тоже могут начать находиться поиском — но ядро подсказок — из собранной базы.

Подсказки в глобальном поиске — это не статический список во фронтенде: при вводе строка уходит в sc-server, который выполняет поиск по содержимому sc-ссылок в уже загруженной SC-памяти. Сами тексты там появляются из собранной базы знаний (kb.bin из sc-models через sc-builder) плюс возможные изменения в рантайме.

askai_core_definitions.scs — это авторский фрагмент SC-модели в sc-models: определения ключевых понятий метасистемы и блоки askai_q_* с вариантами вопросов и ответами для AskAI. Он не генерируется сам системой: его писали вручную, компилятор только включает его в kb.bin. Содержимое — терминология и краткие объяснения вокруг OSTIS/IMS и смежных понятий, согласованные с остальной базой проекта.

Пишу запрос → он обрабатывается в контуре метасистемы (часто sc-web + sc-machine с одной и той же базой в памяти) → по идентификаторам, ссылкам, определениям и т.п. находится фрагмент знаний → пользователю отдаётся текст ответа.

Точнее было бы сказать: не всё идёт одним прямым «запрос на sc-server» — часть идёт HTTP /api/kb/search/, часть — WebSocket к sc-server, но источник знаний один: загруженная SC-память.
